# Онлайн-платформа для ігор з друзями — дизайн прототипу

**Дата:** 2026-08-17
**Джерело вимог:** ТЗ «Онлайн-платформа для ігор з друзями (голосовий чат + міні-ігри)»
**Статус:** затверджено

## 1. Що будуємо

Постійна кімната для компанії друзів: хтось створює кімнату, скидає код або посилання, всі
підключаються до голосового чату, разом обирають гру, грають, після партії лишаються в тому ж
голосовому чаті й обирають наступну. До 10 людей у кімнаті.

Прототип покриває **Must-have і Should-have** з розділу 11 ТЗ:

| Блок | Входить |
|---|---|
| Кімнати | приватні (код + посилання), публічні + room browser з фільтрами, лобі, стани `lobby → in_game → results → lobby` |
| Voice | LiveKit self-hosted, реальне з'єднання, mute/unmute, індикатор «хто говорить» |
| Word-ігри | Alias, Шляпа (режим Alias), Крокодил (word-engine + малювання) |
| Card-ігри | Дурак, Дев'ятка |
| Auth | guest-режим, email-реєстрація, апгрейд гостя до акаунта, Google OAuth за env-флагом |
| Соціальне | профіль, список друзів, запити в друзі, in-app сповіщення |
| Модерація | кік, бан, репорт, rate-limit на створення кімнат |
| Scoreboard | результати партії, історія партій гравця |
| Інфра | Terraform-модулі, Helm-чарти, GitHub Actions — **конфіги без деплою** |

**Свідомо поза обсягом** (розділ 11, Could-have): соціальна дедукція (Мафія/Шпигун), треті ігри
в кожній категорії, решта ігор зі списку 4.1.

## 2. Структура репозиторію

ТЗ у розділі 8.3 задає верхньорівневий розклад `backend/ frontend/ infra/ charts/`, тоді як
типова Nx-конвенція — `apps/*`. Nx дозволяє довільні шляхи проєктів, тому лишаємо розклад ТЗ і
додаємо до нього дві бібліотеки.

```
backend/              NestJS: платформні модулі + runtime ігор + WS-gateway
frontend/             Next.js App Router
libs/shared/          @gp/shared — контракт WS-подій, DTO, типи view-стану
libs/game-core/       @gp/game-core — рушії та визначення ігор, чистий TS
infra/                Terraform (розділ 8.3 ТЗ)
charts/               Helm: backend-api, frontend, livekit
.github/workflows/    ci.yml, backend-deploy.yml, frontend-deploy.yml
docker-compose.yml    postgres, redis, livekit
```

**Правила залежностей** (примусово через Nx module boundaries):

```
frontend  →  shared
backend   →  shared, game-core
game-core →  shared
shared    →  (нічого)
```

`game-core` не має права імпортувати нічого з `backend` чи `frontend`. Це і є «чистий поділ на
платформні та ігрові модулі, які живуть паралельно» з розділу 2.2 ТЗ, зафіксований конфігом, а не
домовленістю.

**Тулінг:** pnpm workspaces, Nx для task graph і кешу, Biome для лінту й формату (розділ 2.2 ТЗ —
Biome, не ESLint), TypeScript strict у всіх проєктах.

## 3. Ігрове ядро

### 3.1 Контракт

Гра — це не клас, який успадковує рушій, а об'єкт з чистими функціями:

```ts
interface GameDefinition<S, A> {
  id: GameId
  meta: {
    title: LocalizedString
    engine: 'word' | 'card'
    minPlayers: number
    maxPlayers: number
    teamBased: boolean
  }
  init(ctx: InitContext): S
  reduce(state: S, action: A, ctx: ActionContext): Effect<S>
  onTimer(state: S, timerId: string, ctx: ActionContext): Effect<S>
  view(state: S, viewerId: PlayerId): PlayerView
  results(state: S): GameResultRow[]
}

interface InitContext {
  players: PlayerId[]
  seed: number
  options: Record<string, unknown>
  deck?: WordDeckSnapshot     // для word-ігор
  now: number
}

interface ActionContext {
  actorId: PlayerId
  now: number
  seed: number
}

type Effect<S> = {
  state: S
  events: GameEvent[]         // для анімацій/тостів на клієнті
  timers?: TimerOp[]          // { op: 'set' | 'clear', id, delayMs }
  finished?: boolean
}
```

Три властивості, заради яких обрано саме такий контракт:

**Серверна авторитетність за конструкцією.** `reduce` — єдина точка, де стан змінюється, і вона ж
валідує, що `ctx.actorId` має право на цю дію. Клієнт не може підробити хід або очки, бо клієнтський
код взагалі не бере участі в обчисленні стану. Це прямо закриває ризик 12.2 ТЗ.

**Секрети не залишають сервер.** `view(state, viewerId)` віддає кожному гравцеві його власну
проєкцію: слово бачить лише той, хто пояснює, карти в руці — лише власник, решта бачить кількість
карт. Клієнт фізично не отримує того, що міг би підгледіти в devtools.

**Детермінованість.** `reduce` не має доступу ні до годинника, ні до `Math.random` — час і seed
приходять у `ctx`. Тому правила Дурака тестуються без сокета, без бази й без Nest-контейнера, а
стан не розповзається між інстансами backend.

### 3.2 Рушії

Рушії — не базові класи, а набори примітивів, які редюсери викликають.

**`word-engine`** (розділ 4.3 ТЗ): черга команд і гравців, стан «хто зараз пояснює», раунд-таймер,
витяг слова зі словника без повторів у межах партії, нарахування очок, перехід ходу.

**`card-engine`** (розділ 4.3 ТЗ): колода на 36 карт, детермінований shuffle за seed, роздача,
визначення козиря, черга ходів, абстракція правила «чим б'ється карта», визначення переможця.

### 3.3 Ігри

| Гра | Рушій | Примітка |
|---|---|---|
| Alias | word | команди, таймер, пояснення словами |
| Шляпа | word | те саме визначення з `mode: 'hat'` — розділ 4.2 ТЗ пропонує саме два режими одного рушія |
| Крокодил | word | + малювання |
| Дурак | card | козир, підкидання, биття, відбій |
| Дев'ятка | card | викладання послідовностей від дев'яток |

П'ять пунктів у меню на двох рушіях — рівно та демонстрація перевикористання, заради якої написано
розділ 4.3.

**Малювання в Крокодилі.** Штрихи полотна навмисно **не** входять у стан редюсера. Вони йдуть
окремим ephemeral WS-каналом (`draw:stroke`), не потрапляють ні в снапшот партії, ні в базу. Інакше
кожен рух миші роздував би стан партії й історію подій. Сервер тримає лог штрихів поточного раунду
в Redis-списку з обмеженням довжини (не в пам'яті процесу — інакше при кількох інстансах backend
учасники бачили б різні полотна); новий або перепідключений учасник отримує його одним `draw:sync`.
Лог скидається на початку кожного раунду.

## 4. Realtime

Socket.IO через `@nestjs/websockets`, Redis-адаптер (`@socket.io/redis-adapter`) для горизонтального
масштабування з розділу 2.4 ТЗ. Namespace `/rt`, кімнати сокета `room:{roomId}`. Авторизація — JWT у
`handshake.auth.token`.

Контракт подій живе в `libs/shared` і використовується обома сторонами (розділ 2.2 ТЗ).

**Клієнт → сервер:** `room:join`, `room:leave`, `room:ready`, `room:chat`, `room:select_game`,
`room:vote_game`, `room:kick`, `room:ban`, `room:transfer_host`, `game:start`, `game:action`,
`draw:stroke`, `voice:token`.

**Сервер → клієнт:** `room:state`, `room:member_joined`, `room:member_left`,
`room:member_updated`, `chat:message`, `game:started`, `game:state` (персоналізований view),
`game:event`, `game:ended`, `draw:stroke`, `draw:sync`, `notification`, `error`.

**GameRuntimeService** — єдиний власник активної сесії. Приймає `game:action`, кличе `reduce`,
зберігає снапшот у Redis, розсилає кожному гравцеві його `view`, тримає таймери через реєстр
`setTimeout` на сесію, а на завершенні пише `GameSession` і `GameResult` у Postgres.

**Життєвий цикл кімнати** (розділ 3.2 ТЗ): `lobby → in_game → results → lobby`. Повернення в лобі
автоматичне. Голосовий чат при цьому не чіпається — LiveKit-з'єднання живе окремо від життєвого
циклу партії, це прямо сценарій 6.1 ТЗ.

**Reconnect** (розділ 9 ТЗ): розрив WS не викидає з партії. Учасник позначається `disconnected`,
місце за ним тримається 45 секунд, після чого `RoomPresenceService` його прибирає. Якщо
відключився той, хто зараз пояснює, раунд-таймер ставиться на паузу до повернення або до
спрацювання grace-періоду.

## 5. Voice

`VoiceService` видає LiveKit AccessToken (`livekit-server-sdk`) з `identity = userId`,
`room = room-{roomId}`, грантами лише на цю кімнату й терміном життя 6 годин. Токен запитується
через `voice:token` і оновлюється клієнтом до закінчення.

На фронті хук `useVoice`: `Room.connect` → публікація мікрофона → підписка на
`RoomEvent.ActiveSpeakersChanged` для індикатора «хто говорить» → mute/unmute.

Локально `livekit-server` піднімається в docker-compose з dev-ключами й `turn.enabled: true`. Той
самий код у продакшені йде на Helm-чарт з розділу 8.2 ТЗ. Якщо `LIVEKIT_URL` не заданий, backend
віддає `voice: { enabled: false }`, і фронт показує панель у стані «недоступно» — прототип
лишається запускним без Docker.

## 6. Дані

Sequelize (`sequelize-typescript`) + міграції + сідери, як вимагає розділ 2.2 ТЗ.

Моделі точно за розділом 7 ТЗ: `User`, `Friendship`, `Room`, `RoomMember`, `GameSession`,
`GameResult`, `WordDeck`.

Додаємо дві таблиці, яких розділ 7 не називає, але без яких він не працює:

- **`WordDeckEntry`** — самі слова. `WordDeck` у ТЗ описано як `(id, category, language)`, тобто це
  лише заголовок словника; слова мають десь лежати.
- **`RoomBan`** — бан з розділу 3.2 ТЗ має зберігатися, інакше забанений повертається за тим самим
  посиланням.

**Redis:** ephemeral-стан активної партії, реєстр активних кімнат, pub/sub між інстансами backend,
rate-limit на створення кімнат.

## 7. Auth

Guest-режим — основний вхід: нікнейм → `User` з `is_guest: true` → JWT. Повноцінна email-реєстрація
поруч (argon2 для паролів). Апгрейд гостя до акаунта — те саме «закріпити реєстрацією пізніше» з
розділу 3.2 ТЗ: guest-користувач додає email і пароль, зберігаючи свій id, друзів та історію.

Google OAuth: стратегія написана, вмикається лише за наявності `GOOGLE_CLIENT_ID` /
`GOOGLE_CLIENT_SECRET`, бо клієнтських креденшелів у прототипі немає.

JWT access (15 хв) + refresh (30 днів) у httpOnly-cookie.

## 8. Frontend

Next.js App Router, Tailwind, Zustand для стану кімнати й партії, типізована обгортка
socket.io-client, i18n uk/en (розділ 9 ТЗ).

| Маршрут | Зміст |
|---|---|
| `/` | лендинг, guest-вхід, «створити кімнату», «ввести код» |
| `/login`, `/register` | email-auth, кнопка Google за флагом |
| `/rooms` | браузер публічних кімнат з фільтрами за грою й вільними місцями |
| `/room/[code]` | одна сторінка, що перемикає лобі / гру / результати за `room.status` |
| `/profile` | профіль, друзі, запити в друзі, історія партій |

Голосова панель рендериться на `/room/[code]` над усіма трьома станами — вона не розмонтовується
при старті й завершенні партії, тому з'єднання не рветься.

Ігрові екрани — окремі компоненти на гру, які отримують `PlayerView` і шлють `game:action`. Спільна
оболонка (таймер, рахунок, черга) — з word/card-скінів, як пропонує розділ 4.3 ТЗ («новий UI-скін
поверх готового рушія»).

## 9. Тести

**`libs/game-core` — Vitest.** Найцінніші тести проєкту, бо це чисті функції:
правила биття в Дураку, повний потік раунду Alias (старт → слово → зараховано → пропуск → таймаут →
зміна пояснювача), детермінованість shuffle за seed, `view()` не протікає секретами.

**`backend` — Jest.** Юніт-тести сервісів (коди кімнат, rate-limit, grace-період reconnect) плюс
один e2e-сценарій через справжній сокет: створити кімнату → зайти двома клієнтами → стартувати
Alias → зарахувати слово → завершити партію → перевірити записи в `GameResult`.

Це прототип, не 100% покриття. Але правила ігор і потік кімнати покриті реально.

## 10. Інфра — конфіги без деплою

Повний набір за розділом 8.3 ТЗ.

**`infra/`:** `main.tf`, `providers.tf`, `variables.tf`, `outputs.tf`, `backend.tf`,
`terraform.tfvars.example`, `modules/{s3-backend,vpc,ecr,eks,rds,redis,ci-cd,argo_cd,monitoring}`.

**`charts/`:** `backend-api/`, `frontend/`, `livekit/` (з `turn.enabled: true` і Service типу
LoadBalancer з прокинутим UDP-рейнджем, розділ 8.2 ТЗ).

**`.github/workflows/`:** `ci.yml` (lint + test + build), `backend-deploy.yml` і
`frontend-deploy.yml` — OIDC-автентифікація в AWS без довгоживучих ключів, `docker buildx` → ECR →
бамп `image.tag` у `values.yaml` → push у гілку, за якою стежить Argo CD (розділ 8.4 ТЗ).

**Перевірка:** `terraform fmt -check`, `terraform init -backend=false && terraform validate`,
`helm lint`. Жодного `apply`, жодного `plan` проти реального AWS — user явно попросив тільки конфіги.

## 11. Ризики й рішення

| Ризик з ТЗ | Рішення в дизайні |
|---|---|
| 12.1 WebRTC-voice — найбільший ризик | LiveKit self-hosted з першого дня, SFU, вбудований TURN; voice за фіче-флагом, щоб решта прототипу не блокувалася |
| 12.2 Синхронізація стану, підробка ходу клієнтом | чисті редюсери на сервері + `view()` як єдиний канал стану до клієнта |
| 12.3 Переоцінка перевикористання рушіїв | перша гра в категорії свідомо дорожча; Шляпа як режим Alias і Дев'ятка на card-engine — дешеві підтвердження, що рушій справді перевикористовний |

## 12. Порядок робіт

Вертикальні потоки з розділу 10 ТЗ, але виконуються послідовно одним виконавцем:

1. Фундамент — Nx-монорепа, Biome, TS, docker-compose, `libs/shared`
2. Дані — Sequelize-моделі, міграції, сідери словників uk/en
3. Auth — guest, email, апгрейд, JWT, OAuth за флагом
4. Кімнати — CRUD, коди, публічні/приватні, room browser, модерація
5. Realtime — WS-gateway, presence, reconnect, чат
6. `game-core` — word-engine, card-engine, Alias/Шляпа, Дурак (+ тести)
7. Runtime — виконання ігор на backend, таймери, персист результатів
8. Voice — LiveKit токени й клієнтська інтеграція
9. Frontend — усі екрани
10. Крокодил і Дев'ятка — підтвердження перевикористання рушіїв
11. Друзі, сповіщення, scoreboard
12. Інфра — Terraform, Helm, GitHub Actions
13. README, фінальна перевірка

Якщо обсяг доведеться різати, найдешевше знімаються Дев'ятка й друзі — від них нічого не залежить.
